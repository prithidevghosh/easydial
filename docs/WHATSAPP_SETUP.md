# EasyDial WhatsApp pilot — setup and live verification

Updated 2026-11-21. WhatsApp code is implemented and locally tested. Actual Meta delivery and OpenAI voice/intent calls have NOT been verified: credentials are still missing. This is a one-user pilot using the owner's saved grocery accounts, not a public multi-user service. iOS feature work is paused. No purchase or payment is enabled.

## What you need to do versus what the agent can do

The agent can build/configure the integration, navigate Meta setup, fill EasyDial app fields, prepare the webhook server, and run authorized tests. You must sign in to your Meta/Facebook account yourself and handle any identity checks, phone verification, and review/accept account terms. Do not send passwords, tokens or OTPs in chat. Business identity/contact details must be supplied or confirmed by you rather than invented.

For initial testing, use Meta's provided test sender. You do not need to buy a dedicated EasyDial number yet. Add your own WhatsApp phone as the test recipient. Later, a dedicated business sender requires Meta's applicable registration and verification steps; public launch also needs resolution of the use-case eligibility gate in WHATSAPP_FEASIBILITY.md.

## 1. Meta account and app

1. Open [Meta's WhatsApp overview](https://developers.facebook.com/documentation/business-messaging/whatsapp/overview). Choose **Login** and sign in using Facebook or a managed Meta account.
2. Open the app dashboard. Choose **Create App**, name it **EasyDial**, and choose **Connect with customers through WhatsApp**. Use your actual contact email and an appropriate business portfolio (create one if required).
3. Follow any developer-registration, account-security and terms screens yourself. These steps vary by account; don't assume business verification or public-launch approval is already complete.
4. Under **Use cases → Customize → WhatsApp / API Setup** (some accounts show **WhatsApp → API Setup**), use the test sender. Add your own phone as a recipient and complete verification on your device.
5. Collect the **Phone Number ID** and generate the test **access token**. Phone Number ID is Meta's internal ID, not the visible phone number. In **App settings → Basic**, find the **App Secret**. Temporary tokens expire; replace them when needed. Production needs an appropriate maintained access token, not a test token baked into source.

Official [getting-started guide](https://developers.facebook.com/documentation/business-messaging/whatsapp/get-started) and [webhook guide](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/create-webhook-endpoint).

## 2. Save credentials locally

From the repository root in your terminal:

```sh
uv --directory backend run python tools/connect_whatsapp.py
```

This helper hides typed inputs, preserves existing store settings, creates a random webhook verification token when needed, and writes only to ignored `backend/.env` with owner-only permissions. It does not send any messages or make API calls.

| Field | Get it from |
| --- | --- |
| WHATSAPP_PHONE_NUMBER_ID | Meta app → WhatsApp API Setup → Phone Number ID |
| WHATSAPP_ACCESS_TOKEN | Meta API Setup → Generate access token |
| META_APP_SECRET | Meta app → App settings → Basic → App Secret |
| WHATSAPP_ALLOWED_SENDER | Your verified recipient phone number, country code plus digits, without `+`, spaces or punctuation |
| WHATSAPP_SUPPORT_CONTACT | Your actual support email or phone, which the bot shows to the test user |
| OPENAI_API_KEY | Your OpenAI API project's API keys page; billing and model access must be available |
| WHATSAPP_VERIFY_TOKEN | Generated by the helper; copy privately from `.env` into Meta's webhook Verify token field |

`WHATSAPP_API_VERSION` defaults to `v27.0`, matching the current official documentation examples used for this implementation. It is configurable. `WHATSAPP_DATABASE` defaults to `.state/whatsapp/pilot.sqlite3` relative to the backend working directory. Neither setting is a token.

Check presence without displaying values:

```sh
uv --directory backend run python tools/connect_whatsapp.py --check
```

On this Mac, FFmpeg and the existing store address/profiles are already present. OpenAI and Meta credentials remain required. Presence checks are not remote credential validation.

## 3. Start the isolated webhook service

Stop the old EasyDial API/store worker before testing commerce through WhatsApp. Only one process may use each saved Chrome profile. Do not run login helpers, live smoke scripts and the WhatsApp worker against those profiles simultaneously.

```sh
uv --directory backend sync --locked
uv --directory backend run python -m easydial.whatsapp
```

This starts `http://127.0.0.1:8001`. The server exposes only `/health` and GET/POST `/webhooks/whatsapp`; it does NOT expose the iOS session API. It uses one process and disables access logs so the GET verification token is not recorded in URLs. If Meta settings are incomplete, health reports `setup_required` and ingress returns 503. Restart after changing `.env`.

Use a public HTTPS tunnel for this local test, for example with the already installed Cloudflare CLI in another terminal:

```sh
cloudflared tunnel --url http://127.0.0.1:8001
```

Take the HTTPS URL reported by that process and append `/webhooks/whatsapp`. The tunnel URL changes when recreated. The computer and both processes must stay awake. Do not tunnel port 8000 or the general session API. A temporary tunnel is a development setup, not production hosting.

## 4. Connect the callback in Meta

Under **WhatsApp → Configuration** or **Use cases → Customize → Configuration**:

- Callback URL: `https://YOUR-ACTUAL-TUNNEL-HOST/webhooks/whatsapp`.
- Verify token: the exact `WHATSAPP_VERIFY_TOKEN` in your private `.env`.
- Save/verify and subscribe to the **messages** webhook field for the messaging account.

The server checks Meta's challenge and validates POST payloads using `X-Hub-Signature-256` and the App Secret. It ignores other phone-number IDs and all senders except the single configured tester. Username/BSUID-only senders are not supported in this phone-number-bound pilot and are ignored; do not claim general-user coverage.

Use your own verified WhatsApp account to initiate the chat with the Meta test number. This opens the customer-service window. No unsolicited initial message is needed from the agent. This implementation replies only within the window and does not send approved templates outside it.

## 5. Live acceptance test — no orders

1. Send **Hi** to the test number. Expect the EasyDial introduction and support contact.
2. Send a short voice note, for example asking for two packs of a specific milk and one bread. Audio must be at most 60 seconds and 8 MB. Test with one language first, then actual Hindi/Hinglish and regional-language recordings.
3. Confirm actual products/prices from both stores appear. Choose by menu, typed number, or an unambiguous spoken choice. For a multi-product request, remaining options are narrowed to the chosen store because the existing controller permits one store per basket.
4. Ask to increase a quantity, remove an item or replace a brand. Verify the displayed draft. A comparison question must not add products.
5. Tap **Review basket** or ask to review. This is the first store-cart synchronization step. Verify every item, quantity, delivery address, fee and total against the provider website.
6. Tap **Checkout · Pending**. Expect explicit Pending and no order/payment. This calls only the existing local confirmation boundary.
7. Remove all draft items and review again to clear only the cart owned by this session. Verify the store cart is empty. Never clear an unrelated/external cart to make a test pass.
8. Test an old selection button, repeated webhook, expired store session and a correction after review. Outdated reviews must not remain valid.

Outgoing responses currently use text, product lists and buttons. Incoming voice is implemented; spoken replies and fully localized fixed UI/bill strings remain future improvements. OpenAI handles Indian-language interpretation, but no all-language accuracy claim is justified until real recordings are measured.

## 6. Inspect failures without exposing customer data

```sh
uv --directory backend run python tools/whatsapp_status.py
```

This prints only event/outbox status counts and delivery status counts. It does not print phone numbers, tokens, transcripts, addresses or bills.

- `queued`: durable work awaiting the single worker.
- `done` / `rejected` / `failed`: processed, safely rejected, or operation failed.
- `interrupted`: process stopped during a turn; it is NOT replayed automatically. The next inbound turn gets recovery guidance.
- `sent`: Meta accepted a message ID, not proof it reached the phone. Delivery/read receipts are tracked separately.
- `uncertain`: an outbound timeout/crash may have occurred after Meta accepted the message. No blind resend occurs. Inspect the WhatsApp conversation and credentials before retrying.
- `expired`: no free-form reply outside the customer-service window. Ask the user to message again.

After restart, draft/session/choice state survives but browser cart ownership does not. Existing provider guards refuse to silently adopt a nonempty cart. Reconcile the cart manually before proceeding; do not delete the database as an automatic recovery technique. Changing the sender, account, address or profile configuration requires a new private database and deliberate account onboarding.

State is stored in an owner-only local SQLite file, not an encrypted production database. Completed raw event payloads are cleared; bounded conversation/basket state and message IDs remain. Temporary audio files are deleted after conversion. No automated retention/deletion service or multi-user isolation layer is shipped. Keep this pilot restricted to the owner and keep `.env`/`.state` out of Git.

## Verification evidence

Local result: **43 tests passed**, including 13 WhatsApp tests and five optional Chrome DOM checks; Ruff passes. CI installs FFmpeg so the decoder checks run there as well.

Automated tests cover authenticated webhook challenge/signature, wrong sender/account rejection, duplicate events, stale selections, atomic edits, late messages, voice orchestration using mocked transcription, cart review/Pending with fixture providers, multi-item choice continuation, persistence/interrupted-work handling, uncertain sends, 24-hour-window checks, status-receipt handling, media-host restrictions, Meta HTTP payload contracts and real FFmpeg OGG/Opus decoding/duration rejection.

These are local integration/contract tests. They do not establish actual Meta delivery, OpenAI transcription quality or the complete WhatsApp-to-live-store journey. Existing browser verification is recorded separately in BROWSER_VERIFICATION.md. Payment is not implemented.
